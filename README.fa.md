## شرح مسئله

یکی از سرویس‌های محیط Production دچار خطا شده و کاربران هنگام استفاده از آن با خطای HTTP 500 مواجه می‌شوند.

هدف این چالش، پیاده‌سازی یک ایجنت هوشمند تحلیلگر لاگ است که بتواند مانند یک مهندس DevOps ارشد عمل کند:

1. سؤال کاربر را دریافت کند.
2. تشخیص دهد برای پاسخ‌دادن به سؤال باید از چه ابزاری استفاده شود.
3. پارامترهای مناسب ابزار را از درخواست کاربر استخراج کند.
4. از طریق پروتکل MCP به سرور متصل شود.
5. لاگ‌های موردنیاز را دریافت کند.
6. علت اصلی خطا را شناسایی کند.
7. نتیجه را به زبان ساده، شفاف و قابل‌فهم به کاربر گزارش دهد.

برای حل چالش باید دو بخش اصلی با .NET 10 پیاده‌سازی شوند:

- **MCP Server**
- **AI Agent Client**

## بخش اول: MCP Server

یک برنامه .NET ایجاد کنید که نقش MCP Server را بر عهده داشته باشد و ابزار زیر را در اختیار Agent قرار دهد.

### ابزار `GetLogs`

#### نام ابزار

```text
GetLogs
```

#### توضیح پیشنهادی ابزار

```text
Returns application logs for a specified service within a requested time range.
```

#### ورودی‌ها

| پارامتر | نوع | الزامی | توضیح |
|---|---:|:---:|---|
| `serviceName` | `string` | بله | نام سرویسی که باید لاگ‌های آن بررسی شود |
| `minutesAgo` | `int` | بله | تعداد دقایق گذشته برای جستجوی لاگ‌ها |

نمونه ورودی:

```json
{
  "serviceName": "PaymentService",
  "minutesAgo": 15
}
```

#### خروجی مورد انتظار

ابزار باید داده‌ای شبیه‌سازی‌شده از Elasticsearch برگرداند که حداقل شامل خطای زیر باشد:

```text
[ERROR] - PaymentService - Database connection timeout after 30000ms on SQL-Server-01
```

فرمت خروجی می‌تواند متن ساده یا یک مدل ساخت‌یافته باشد، اما اطلاعات زیر باید در نتیجه موجود باشد:

- سطح لاگ: `ERROR`
- نام سرویس: `PaymentService`
- نوع خطا: `Database connection timeout`
- مدت Timeout: `30000ms`
- سرور مقصد: `SQL-Server-01`

### الزامات MCP Server

- ابزار `GetLogs` باید از طریق MCP قابل کشف و فراخوانی باشد.
- استفاده از SDK رسمی MCP مجاز است.
- ارتباط ترجیحاً از طریق `stdio` انجام شود.
- ورودی‌های نامعتبر باید بدون Crash مدیریت شوند.
- برای `serviceName` خالی یا `minutesAgo` نامعتبر، خطای قابل‌فهم برگردانده شود.
- اتصال واقعی به Elasticsearch الزامی نیست.
- داده لاگ می‌تواند در حافظه، فایل یا یک Provider شبیه‌سازی‌شده نگهداری شود.
- منطق تولید داده شبیه‌سازی‌شده بهتر است پشت یک Abstraction مانند `ILogProvider` قرار گیرد.

## بخش دوم: AI Agent Client

یک Console Application با .NET 10 ایجاد کنید که نقش Agent Client را بر عهده داشته باشد.

کاربر سؤال زیر را مطرح می‌کند:

```text
چرا سرویس پرداخت در ۱۵ دقیقه گذشته خطای ۵۰۰ می‌دهد؟
```

Agent باید درخواست را تحلیل کرده و تشخیص دهد که ابزار `GetLogs` باید با پارامترهای زیر فراخوانی شود:

```json
{
  "name": "GetLogs",
  "arguments": {
    "serviceName": "PaymentService",
    "minutesAgo": 15
  }
}
```

پس از دریافت لاگ از MCP Server، Agent باید علت اصلی خطا را استخراج کرده و یک گزارش قابل‌فهم تولید کند.

### مسئولیت‌های Agent Client

- دریافت سؤال کاربر
- دسترسی به فهرست ابزارهای MCP Server
- انتخاب ابزار مناسب
- استخراج پارامترهای لازم از درخواست کاربر
- ساخت Tool Call
- فراخوانی ابزار از طریق MCP
- دریافت نتیجه ابزار
- تحلیل لاگ
- تولید پاسخ نهایی
- مدیریت خطاهای ارتباطی و ورودی‌های ناقص

---

## سیاست استفاده از مدل زبانی

اتصال به یک مدل زبانی واقعی مانند موارد زیر الزامی نیست:

- OpenAI
- Azure OpenAI
- Ollama
- GitHub Models
- هر ارائه‌دهنده دیگر

شرکت‌کنندگان می‌توانند برای اجرای آفلاین و تست‌پذیر پروژه از `Fake` یا `Mock Model` استفاده کنند.

با این حال، شرایط زیر الزامی است:

1. Provider مدل یا Agent باید پشت یک Interface یا Abstraction قرار گیرد.
2. جایگزینی Mock با یک مدل واقعی نباید نیازمند تغییر منطق اصلی برنامه باشد.
3. خروجی Agent باید مفهوم Tool Call را نمایش دهد.
4. Agent باید مسئول انتخاب ابزار و تولید پارامترهای آن باشد.
5. Console Application نباید مستقیماً تصمیم بگیرد که `GetLogs` را با مقادیر ثابت فراخوانی کند.
6. پاسخ نهایی نباید به‌صورت یک رشته ثابت از قبل در کد قرار گرفته باشد.

نمونه Abstraction پیشنهادی:

```csharp
public interface IAgentModel
{
    Task<AgentDecision> DecideAsync(
        string userMessage,
        IReadOnlyCollection<AvailableTool> tools,
        CancellationToken cancellationToken);
}
```

نام Interface و مدل‌ها اختیاری است و شرکت‌کننده می‌تواند طراحی متفاوتی ارائه دهد.

### پیاده‌سازی‌های قابل قبول

- اتصال واقعی به LLM و استفاده از Tool Calling
- استفاده از Mock Model که یک Tool Call استاندارد تولید می‌کند
- یک Parser عمومی و قابل توسعه برای تحلیل درخواست و ساخت Tool Call
- استفاده از Configuration یا Metadata برای نگاشت نام فارسی سرویس به نام فنی آن

### پیاده‌سازی‌های غیرقابل قبول

نمونه زیر Hard-code محسوب می‌شود:

```csharp
if (userMessage.Contains("پرداخت"))
{
    await GetLogs("PaymentService", 15);
}
```

موارد زیر نیز پذیرفته نیستند:

- فراخوانی مستقیم `GetLogs` از Console Application
- قرار دادن کامل Tool Call به شکل ثابت برای تنها سؤال نمونه
- قرار دادن پاسخ نهایی به شکل ثابت در کد
- دورزدن MCP و استفاده مستقیم از کلاس MCP Server
- وابسته‌کردن کامل برنامه به یک Provider بدون امکان جایگزینی

## قوانین و محدودیت‌ها

- پروژه باید با **.NET 10** پیاده‌سازی شود.
- استفاده از SDK رسمی MCP مجاز است.
- استفاده از یک LLM واقعی اختیاری است.
- پروژه باید بدون نیاز اجباری به API Key قابل بررسی و اجرا باشد.

- ارتباط Agent و ابزار باید از طریق MCP انجام شود.
- Hard-code کردن Tool Call یا پاسخ نهایی ممنوع است.
- برنامه باید ورودی نامعتبر و خطای ارتباطی را بدون Crash مدیریت کند.
- تمام پروژه‌ها باید با یک دستور استاندارد `dotnet build` قابل Build باشند.
- نام‌گذاری، ساختار و طراحی داخلی آزاد است، مشروط بر اینکه الزامات چالش رعایت شوند.

### ۱. صحت عملکرد و تکمیل سناریوی اصلی — ۳۰ امتیاز

- اجرای کامل سناریوی سؤال کاربر
- استخراج صحیح نام سرویس
- استخراج صحیح بازه زمانی
- دریافت لاگ از MCP Server
- تشخیص صحیح علت خطا
- تولید گزارش نهایی قابل‌فهم

### ۲. پیاده‌سازی MCP Server و ابزار `GetLogs` — ۲۰ امتیاز

- ثبت صحیح ابزار
- تعریف مناسب نام، توضیحات و پارامترها
- برقراری ارتباط واقعی از طریق MCP
- استفاده صحیح از `stdio` یا Transport معتبر دیگر
- اعتبارسنجی ورودی‌ها
- جداسازی مناسب Log Provider از MCP Tool

### ۳. طراحی Agent، انتخاب ابزار و جلوگیری از Hard-code — ۲۰ امتیاز

- وجود لایه Agent یا Model Abstraction
- انتخاب ابزار در لایه Agent
- تولید Tool Call
- امکان جایگزینی Mock با LLM واقعی
- عدم فراخوانی مستقیم ابزار از Console
- عدم Hard-code کردن پاسخ یا پارامترهای نهایی

> اتصال به LLM واقعی امتیاز اضافه مستقلی ندارد. یک Mock Model با معماری صحیح می‌تواند امتیاز کامل این بخش را دریافت کند.

### ۴. معماری، کیفیت کد و قابلیت تست — ۱۵ امتیاز

- نام‌گذاری مناسب

- استفاده مناسب از `async/await`
- رعایت Cancellation Token در بخش‌های لازم
- امکان توسعه و جایگزینی اجزا

### ۵. تست‌ها، اعتبارسنجی و مدیریت خطا — ۱۰ امتیاز

- تست Tool Call
- تست ورودی نامعتبر
- تست تحلیل لاگ
- مدیریت خطای ارتباط با Server
- عدم نمایش Stack Trace خام به کاربر نهایی

### ۶. مستندات و کیفیت ارسال — ۵ امتیاز

### اثر Hard-code بر ارزیابی

- فراخوانی مستقیم `GetLogs` از Console: امتیاز بخش Agent صفر می‌شود.

- پاسخ نهایی ثابت: امتیاز تحلیل و گزارش نهایی تعلق نمی‌گیرد.
- پارامترهای ثابت مخصوص سؤال نمونه: امتیاز استخراج پارامترها تعلق نمی‌گیرد.
